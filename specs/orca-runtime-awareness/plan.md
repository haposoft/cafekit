# Orca awareness ships with the CafeKit install
Specs-Contract: process-first-ready-v1

## Scope decision (C1 — 2026-09-13)
- Existing: one `SKILL.md` under `src/claude/skills/<name>/` reaches Claude Code (`.claude/skills`, and Grok through its Claude compatibility) and Codex (`.agents/skills`, frontmatter `name` rewritten to `cf-<name>` by `bin/lib/codex-install.js:247`) through `bin/phases/copy-payload.js:85,132`, which copies skills only for platforms whose `capabilities.skills` is true. omp's is false by design (`bin/lib/context.js:130-132,143-150`): omp discovers `.claude/skills` and `.agents/skills` itself, so it sees a CafeKit skill only when Claude or Codex is installed in the same project. The default install set is `skills.required` in `src/claude/migration-manifest.json:8`. Rules under `src/claude/rules/` are copied to `.claude/rules`, `.codex/rules`, and `.omp/rules` by `copyRulesDirectory` (`bin/phases/claude-runtime.js:261`); Claude Code loads `.claude/rules` itself, Codex reads them through the pointer at `src/codex/AGENTS.md:10-11`. `src/claude/hooks/session.cjs:252-258` and `src/codex/hooks/session.cjs:94-99` print a `Type | PM | Framework | Branch` line at SessionStart. Orca serves its own version-matched guides locally: `orca skills get orca-cli` and `orca skills get orchestration`, `--references` to list a topic's sub-references and `--reference <name>` to print one, all read from the registry bundled in the CLI.
- Minimum change: a `cf:orca` skill in the payload that detects `ORCA_PANE_KEY`, maps the user's phrases to the two Orca guides, tells the agent to read `orca skills get …` for the exact commands, bounds what it may send to another pane, treats what it reads from other panes as untrusted, and draws the Orca/Herdr boundary; `orca` in `skills.required` and in the packed-payload guard; one neutral row in `skill-domain-routing.md`; one `Orca: pane` part in both SessionStart lines when the variable is present; tests, docs, README bullet, changelogs.
- Expansion signals: about ten touched files, above the eight-file threshold; one subsystem — every piece rides an existing pipeline.
- User decision: C1 KEEP. EXPAND (a `--with-orca` installer flag running `orca skills install --local`) was declined: that command resolves to `npx --yes skills add https://github.com/stablyai/orca …`, a network fetch during an installer that today runs from the tarball alone. CUT (rule and session line only, no skill) was declined: without a skill there is no home for the user's vocabulary, the authority boundary, or the Herdr boundary.

## Why this is wanted
The user runs Claude Code, Codex, Grok, and omp inside Orca panes across many projects and has had to open every session with "I am using Orca; go read its docs, then watch the Codex pane". A per-machine setup (Orca's skills under `~/.agents/skills` plus a personal bridge skill) was tried on 2026-09-11 and removed on 2026-09-13 at the user's request: it followed the machine, not the project. Nothing in Orca injects context into a session — its per-agent hooks under `~/.orca/agent-hooks/*.sh` only spool events back to Orca — so the agent cannot know on its own.

## Verified contract (Orca CLI on this host, 2026-09-13)
- Binary: `/usr/local/bin/orca`, CLI 1.4.200; this pane was launched by app 1.4.198. `orca --help` lists `terminal list / show / read / send / wait / create / rename / split / switch / close`, `worktree …`, `orchestration …`, `skills list / get / install / installed / share`, `agent-context`.
- `orca skills list` names eight topics: `computer-use`, `linear-tickets`, `orca-cli`, `orca-emulator`, `orca-emulator-android`, `orca-linear`, `orca-per-workspace-env`, `orchestration`. `orca skills get <topic>` prints the bundled guide; `orca skills get <topic> --references` lists its sub-references (`orca-cli`: `automations`, `browser`, `publishing`); `orca skills get <topic> --reference <name>` prints one. `--help` states "Reads bundled guide content locally without contacting the Orca runtime"; with `HTTPS_PROXY`/`ALL_PROXY` pointed at a dead port the command still returns 221 and 201 lines with exit 0.
- **The guide text moves with the CLI version.** Between 2026-09-11 and 2026-09-13 the `orca-cli` guide kept its 221 lines but changed its opening: an `ORCA_CLI_COMMAND` rule read on the 11th is gone; today it says `ORCA` is a placeholder for the executable resolved in the stub, dev builds use `orca-dev`, and "if the CLI is missing, say so explicitly instead of inspecting source files first". The skill therefore quotes nothing from the guide; it points at the commands that print it.
- `orca skills install` resolves to `npx --yes skills add https://github.com/stablyai/orca --skill … --global|--local --agent …`; it is the only network path and this packet does not use it.
- `orca terminal list --json` on this host returns fifteen terminals across five repositories; `orca terminal send --terminal <handle> --text … --enter` accepts any of them. Handles are runtime-scoped identifiers, not credentials: `env -i … orca terminal list` still lists them, so authority comes from being able to execute `orca` on the machine, not from the environment.
- Environment inside an Orca pane (observed, 16 variables): `ORCA_PANE_KEY`, `ORCA_TERMINAL_HANDLE`, `ORCA_TAB_ID`, `ORCA_WORKTREE_ID`, `ORCA_WORKSPACE_ID`, `ORCA_APP_VERSION`, `ORCA_AGENT_HOOK_ENDPOINT`, `ORCA_AGENT_HOOK_PORT`, `ORCA_AGENT_HOOK_TRANSPORT`, `ORCA_AGENT_HOOK_VERSION`, `ORCA_AGENT_HOOK_ENV`, `ORCA_AGENT_LAUNCH_TOKEN`, `ORCA_AGENT_HOOK_TOKEN`, `ORCA_USER_DATA_PATH`, `ORCA_PI_SOURCE_AGENT_DIR`, `ORCA_OPENCODE_CONFIG_DIR`. `ORCA_PANE_KEY` is the presence marker this packet keys on; it is observed, not documented by Orca (`orca skills get orca-cli | grep ORCA_PANE_KEY` is empty). `ORCA_AGENT_HOOK_TOKEN` and `ORCA_AGENT_LAUNCH_TOKEN` are credentials; no CafeKit hook reads them today (`writeEnv` in `session.cjs:30-41` writes a fixed list of thirteen keys) and none will.
- Orca's own hooks for Claude Code live in `~/.claude/settings.json` (13 groups calling `~/.orca/agent-hooks/claude-hook.sh`) and only spool the event payload to Orca.
- Herdr is a different tool: `/opt/homebrew/bin/herdr`, skill `herdr-orchestrator` symlinked from `~/.hod/skill`, active only with `HERDR_ENV=1`.

### `[UNVERIFIED]` — recorded as limitations; no acceptance criterion depends on them
- **Codex context delivery.** `src/codex/hooks.json:4-16` registers the session hook at SessionStart; nothing observed shows Codex feeding its stdout to the model. AC-02 asserts the line is printed, not read. Settle: one Codex session in a CafeKit-installed project inside an Orca pane.
- **omp rules.** The omp binary loads `.omp/rules/*.md` through its native provider but parses each as a TTSR rule (`alwaysApply`, `globs`, `condition`); CafeKit rules carry no frontmatter. Settle: open omp in an installed project and ask which rules it loaded, or `omp ttsr scan -r .omp/rules/skill-domain-routing.md src/`.
- **Grok skill discovery.** `grok inspect` lists the existing `cf-*` skills as `project [claude]`; the new file has not been observed there. Settle: `grok inspect` after install.
- **Codex hooks receive `ORCA_*`.** The hook runs under the Codex process and inherits its environment; observed for the omp bridge (`cafekit-bridge.mjs:145` forwards `process.env`), inferred for Codex.

## Out of scope
- Vendoring Orca's guides, a `.grok`/`.orca` runtime directory, or any network fetch at install time; the skill reads `orca skills get` at use time, so the text is always the installed CLI's own.
- `cafekit-bridge.mjs:210`: making the omp bridge forward `session_start` stdout would give omp the `Orca: pane` line. The user chose to record the gap rather than reopen the omp packet's file.
- Shipping `cf:orca` into `.omp/skills` for omp-only installs; that would reverse the omp packet's "no skill payload" decision.
- The `delegate` skill and any change to how CafeKit dispatches work to external CLIs.
- Making Orca a `PLATFORMS` entry or an installer alias; Orca is a host the agents run inside, not a runtime CafeKit installs into.
- Herdr: no skill, rule, or hook change; the new skill only states the boundary.
- The root `README.md`: the previous core-skill packets list skills only in `packages/spec/README.md` (root has no `cf:loop`), and this one follows that.
