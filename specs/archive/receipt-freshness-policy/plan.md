# Receipt freshness policy
Specs-Contract: process-first-ready-v1

## Scope decision (C1 — revised 2026-09-02)

- Existing: a receipt is bound to live provenance by `receiptValidatorOptions`, which recomputes the runtime context on every call (`workflow-policy.cjs:282-283`) and publishes the current pair as `expectedProvenance` (`:291`); `validateCanonicalReceipt` then requires byte equality (`:1984-1991`). The binding is switched on inside `canonicalFailures`, which hard-codes `requireProvenanceBinding: true` (`spec-receipt.cjs:180-186`), and `checkWorkflowTaskReceipt` fails again when no expected pair survives (`spec-receipt.cjs:269`). The gate applies this to every done task of every completed packet (`spec-gate.cjs:132-146`, `spec-receipt.cjs:313-334`) and again to every done task of an active packet (`spec-gate.cjs:237-244`). `validateCanonicalReceipt` already documents a second mode: without expected values it validates schema only and claims no identity binding (`workflow-policy.cjs:1953-1954`).
- Measured cause: enumerating the eleven completed packets directly gives 27 done tasks, 27 failing, and the failure tally `{"provenance": 27}`; no receipt fails any other check, and all 27 files match their committed bytes. Separately, 22 of the 89 commits between 2026-08-18 and 2026-09-02 touch only the specs root. The completed-set branch is unreachable while this packet has open tasks, because the resolver returns the single unfinished packet (`spec-resolver.cjs:901`), so the measurement must be reproduced by enumeration rather than by observing a live Stop.
- What the binding actually is: a **freshness** check, not an anti-fabrication check. The installed provenance CLI returns a valid `Base`/`Head` pair in under a second without running any verification (`provenance.cjs:283-315`), so a receipt whose command never ran can carry a correct pair and pass. That is true today and stays true after this change; the comparison at `workflow-policy.cjs:1984-1991` compares strings, and nothing proves a command executed. The gate detects drift between a receipt and the tree, not invention.
- Minimum change: bind a receipt to live provenance while it is being written, and stop rebinding it once it is committed and the tree is clean. A done task is validated on structure alone only when three conditions hold together: reading `HEAD:<task path>` succeeds, those bytes equal the file on disk, and `git -C <project root> status --porcelain --untracked-files=all -- . ':(exclude,literal)<specs root>'` is empty. Every git call pins the repository root from `runtimeContext.project_root` rather than the process working directory, and reuses the `:(exclude,literal)` magic already used by `gitBase` (`provenance.cjs:88-91`). Structure-only additionally requires every index entry outside the specs root to carry the plain cached tag, because `git status` honors the `skip-worktree` and `assume-unchanged` flags and would otherwise report a modified tree as clean. Any other outcome keeps today's full binding, including an unreadable or unborn `HEAD`, an untracked or staged-but-uncommitted task file, any uncommitted change outside the specs root, and any change hidden behind an index flag.
- Rejected at C1 with evidence, after an adversarial round found nine Critical defects in the first plan: narrowing `Head` to task-owned paths never reaches the gate, because `recomputeRuntimeProvenance` replays exactly six fields and drops any new input (`provenance.cjs:260-270`); it would not remove churn anyway, because `Base` stays global (`provenance.cjs:86-103`); and it would move the guardrail onto worker-written prose and worker-writable config, the authority the gate already refuses to grant (`spec-gate.cjs:129`, `:201`). Reconstructing a historical `Head` is impossible, since `manifest()` records porcelain status letters and untracked files (`provenance.cjs:166`, `:194`).
- Expansion signals: none. Three tasks, no new module, no new config key, no schema change, and no migration, because the 27 existing receipts already satisfy every non-provenance check.
- User decision: **KEEP** — validate a committed, unchanged receipt on structure alone while the tree outside the specs root is clean; keep full binding everywhere else. Reaffirmed at C2 on the corrected description above.

## Out of scope

- What `Base` and `Head` mean, and how they are derived. `provenance.cjs` keeps its derivation untouched; execution required hoisting its runtime-state root list into one exported constant so the gate's own cache write is not read as a dirty tree, recorded in task 01.
- Excluding the docs or plans roots from provenance. Superseded: with committed receipts unbound on a clean tree, a docs commit no longer invalidates anything.
- Legacy packets. `spec.json` features, nested tasks, `receipts/<task>.md` and `feature-receipt.md` keep today's behavior; `checkTaskReceipt` (`spec-receipt.cjs:227`) and `checkFeatureReceipt` (`spec-receipt.cjs:340`) keep `requireProvenanceBinding: true`.
- Gate cache semantics. The cache stays an optimization and gains no authority (`spec-gate.cjs:228-231`).
- Making the gate detect a fabricated receipt. Named as a limitation below, not solved here.
- Refreshing existing receipts. None is needed and none is authored.

## Risks

- **The gate does not detect invention, in either mode.** A correct `Base`/`Head` pair costs one command and no verification run, so neither today's binding nor this change catches a receipt written for a command that never ran. This change removes a freshness check and the churn it causes; it does not remove a protection the code ever had. The limitation is recorded in the skill's Machine boundary section by task 03 so no operator infers a guarantee.
- **After-the-fact drift is no longer detected on a clean committed tree.** Once a receipt is committed and the tree is clean, editing the implementation in a later commit does not re-invalidate it. The clean-tree condition means that edit must itself be committed first, so the change is at least recorded in history; the `skip-worktree` and `assume-unchanged` index flags cannot be used to present a modified tree as clean, because structure-only also requires every index entry outside the specs root to carry the plain cached tag.
- **A sparse checkout never reaches structure-only.** Paths outside the cone carry
  the `skip-worktree` index tag, which the tag rule rejects, so such a worktree keeps
  full binding permanently. That is fail-closed and costs only the benefit.
- **Structure-only requires a clean tree, which is a workflow constraint.** A receipt written mid-task stays under full binding until the work is committed. Parallel waves defer commits and require user authorization (`parallel-waves.md:11`, `:37`, `:69-72`), and the core chain commits after test and review, so receipts stay bound through those windows. This packet does not change who may commit; it only defines when the binding stops applying.
